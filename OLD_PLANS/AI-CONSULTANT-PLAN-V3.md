# План: ИИ-консультант на `ai.amasters.ru` (версия 3)

Версия 3 опирается на требования `AI-CONSULTANT.md`, план v2 (`AI-CONSULTANT-PLAN.md`) и независимую рецензию `AI-CONSULTANT-PLAN-V2-REVIEW.md`. Существующие документы не менялись.

## Что изменено относительно версии 2

1. **Сквозной адрес абзаца:** разведены локальный HTML-якорь на странице выпуска (`d{d}-p{p}`) и глобальный идентификатор абзаца в API, промпте, схеме ответа и золотом наборе (`{slug}#d{d}-p{p}`). Коллизия одинаковых `d1-p2` из разных выпусков исключена.
2. **Метаданные в промпте и атрибуция кодом:** модель получает не голый `{ id, text }`, а абзац вместе с автором, типом документа, названием, датой создания, подписью выпуска и списком дублей `alsoIn`. Свободное поле `attributedTo` убрано из ответа модели — подпись авторов и типов строит код по `paragraphIds[]`.
3. **Упрощён смысловой поиск (без `pgvector`):** на 34 796 абзацах векторы (`512` `float32`, ~71 МБ) хранятся в обычной колонке `bytea` в PostgreSQL и сканируются точно в памяти Node (`Float32Array`) за ~10 мс. Не нужны пакеты `pgvector` на PG16 (Москва) и PG18 (Амстердам), правка apt-pinning PGDG и права суперпользователя при учебном восстановлении бэкапа.
4. **Один маршрут `POST /api/ask`:** отдельный `POST /api/search` убран. При выключенном ИИ, в Фазе 2, при исчерпанном бюджете или ошибке прокси тот же маршрут отдаёт найденные карточки абзацев с полем `answer: null` и явным кодом причины.
5. **Каталожные вопросы и чистота данных корпуса:** учтены 260 абзацев-разделителей `_____` в `parts.body` (`is_separator`), 6 расколотых `authorSlug` (включая Господа Майтрейю и Сераписа Бея) и отдельный режим выдачи списка документов (`catalog_list`) с полем `description`.
6. **Атомарность и защита в проде:** транзакционный `db:seed` в основном проекте (убирает частичное состояние при `sync` и гонку 308-редиректов на `amasters.ru`), атомарное резервирование дневного бюджета `usage_day` до вызова OpenAI, `maxRetries: 0` на интерактивном запросе, `trust proxy` за `nginx`, отдельный токен в `amster/openai-proxy` с `xfwd: false`, синхронизация списка бэкапов и сторожа сразу на **обоих** серверах.
7. **Проверяемость каждого этапа:** `check:links` сверяет не только наличие `id`, но и текст внутри `<p id="...">`; контрактный тест Фазы 1 работает в GitHub Actions без живого Postgres; порядок сбора золотого набора не блокирует Фазу 0; у всех фаз (включая 5 и 6) есть измеримые критерии выхода.

## 1. Контракт данных и адресов

### 1.1. Адрес абзаца

- `d` — `PearlDocument.position`, целое с `1`. На странице выпуска берётся строго из поля `position` базы (не из индекса массива в JSX).
- `p` — номер абзаца в массиве `toBody(content)` из `src/catalogLabels.ts`, целое с `1` (после разреза по `\n{2,}` и отбрасывания пустых строк). Строки-разделители (`_____`, `***`) из `toBody` **не выбрасываются**, чтобы счёт `p` на `amasters.ru` и в консультанте всегда совпадал 1-в-1.
- **HTML-атрибут на странице выпуска:** `id="d{d}-p{p}"` (например, `d1-p15`).
- **Сквозной идентификатор абзаца (`paragraphRef`):** `{slug}#d{d}-p{p}` (например, `2014Q2-1#d1-p15`). Используется во всех ответах API, в промпте модели, в `paragraphIds[]` и в золотом наборе.
- **Полная ссылка:** `https://amasters.ru/pearls/{siteYear}/{slug}#d{d}-p{p}`, где `siteYear` — год публикации выпуска на сайте (не год создания документа).
- Футер выпуска (`parts.footer`) адресов не имеет и в индекс абзацев не входит. Место и дату создания показывают метаданные карточки документа (`creation`).
- Общий беззависимостный модуль `paragraphContract.ts` (`toBodyParagraphs`, `formatParagraphAnchor`, `formatParagraphRef`, `parseParagraphRef`) лежит в обоих репозиториях в идентичном виде и проверяется общей JSON-фикстурой тест-векторов.

### 1.2. Схема БД консультанта (`amasters_ai`, PostgreSQL 16)

Драйвер `pg`, миграции плоскими SQL-файлами в `db/` (как в `amasters_info`).

- `document`:
  - `slug TEXT`, `position INT` — первичный ключ `(slug, position)`;
  - `site_year INT NOT NULL`, `site_sort_date TEXT NOT NULL`, `site_label TEXT`;
  - `document_type TEXT NOT NULL`, `document_title TEXT`;
  - `author_name TEXT`, `author_slug TEXT` (нормализованные канонические значения);
  - `creation_date DATE`, `creation_year INT`, `creation_raw TEXT`;
  - `pearl_raw TEXT`, `description TEXT NOT NULL`;
  - `header_tsv TSVECTOR` (вес `A` — автор, вес `B` — название документа; GIN-индекс).
- `paragraph`:
  - `ref TEXT PRIMARY KEY` (`{slug}#d{position}-p{paragraph_number}`);
  - `slug TEXT NOT NULL`, `position INT NOT NULL` → `FOREIGN KEY (slug, position) REFERENCES document ON DELETE CASCADE`;
  - `paragraph_number INT NOT NULL`, `UNIQUE (slug, position, paragraph_number)`;
  - `text TEXT NOT NULL`;
  - `is_separator BOOLEAN NOT NULL DEFAULT FALSE` (истина для строк `^[_*\-=~\s]+$`);
  - `text_hash TEXT NOT NULL` — SHA-256 нормализованного текста самого абзаца (`ё → е`, схлопнутые пробелы, нижний регистр) — для склейки дублей и оценки `eval`;
  - `window_hash TEXT NOT NULL` — SHA-256 окна `prev + "\n\n" + curr + "\n\n" + next` (где `prev`/`next` — ближайшие абзацы того же документа с `is_separator = FALSE`);
  - `body_tsv TSVECTOR` (конфигурация `russian` по тексту с нормализацией `ё → е`, пустой для `is_separator = TRUE`; GIN-индекс).
- `embedding` (создаётся сразу или в Фазе 3, без внешнего ключа на `paragraph`, чтобы переживать пересборку корпуса):
  - первичный ключ `(model, window_hash)`;
  - `dims SMALLINT NOT NULL`, `vector BYTEA NOT NULL` (`Float32Array`, little-endian, L2-нормированный), `created_at TIMESTAMPTZ`.
- `usage_day`:
  - `day DATE PRIMARY KEY` (календарная дата `Europe/Moscow`);
  - `ai_calls INT NOT NULL DEFAULT 0`, `input_tokens BIGINT NOT NULL DEFAULT 0`, `output_tokens BIGINT NOT NULL DEFAULT 0`.
- `request_log`:
  - `id BIGSERIAL PRIMARY KEY`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `route_kind TEXT` (`answer` | `catalog_list` | `search_only` | `refused`), `ai_status TEXT` (`ok` | `disabled` | `budget_exceeded` | `busy` | `weak_evidence` | `refused` | `error`), `refusal_reason TEXT`, `paragraphs_count SMALLINT`, `latency_ms INT`, `input_tokens INT`, `output_tokens INT`. **Текст вопроса и IP не хранятся.**

### 1.3. Поток обработки `POST /api/ask`

Вход (Zod): `{ question: string (3..500 знаков), authorSlug?: string, documentType?: DocumentType }`.

1. **Входные барьеры:** валидация длины и фильтров; проверка лимита запросов на IP (`trust proxy = 'loopback'`).
2. **Классификация запроса (`classifyQuestion`, детерминированно без LLM):**
   - явный запрос личного руководства, медицинского/бытового совета или генерации диктовки/призыва «от имени» Владыки → немедленный отказ (`aiStatus: 'refused'`, `refusalReason: 'personal_guidance' | 'request_for_dictation'`) без вызова модели;
   - каталожный запрос («какие диктовки/лекции <автора> есть в каталоге…») → выборка из `document` по автору и типу (`routeKind: 'catalog_list'`), отдача карточек документов со ссылками `#d{position}-p1` и `description` (если документов `<= 10` и включён ИИ — дополнительно краткая сводка по их названиям и первым содержательным абзацам);
   - содержательный вопрос по корпусу → шаг 3.
3. **Поиск кандидатов (`is_separator = FALSE`):**
   - нормализация запроса (`ё → е`, удаление стоп-слов, раскрытие ручного словаря синонимов имён и терминов учения);
   - в Фазе 2 — ступенчатый полнотекст по `document.header_tsv || paragraph.body_tsv` (`AND` по группам синонимов → при нехватке результатов кворум `>= 2` значимых групп для вопросов из 3+ слов); в Фазе 3 — RRF-слияние полнотекста и точного косинуса по `Float32Array` в памяти;
   - применение явных фильтров `authorSlug` и `documentType`.
4. **Дедупликация и отбор:**
   - абзацы с одинаковым `text_hash` склеиваются: основным остаётся самый свежий по `site_sort_date`, остальные уходят в его поле `alsoIn[]` (`ref`, `url`, `author`, `siteLabel`);
   - не более `3` абзацев с одного внутреннего документа, всего до `8` абзацев; подряд идущие абзацы одного документа объединяются при отображении в карточке выпуска.
5. **Порог слабости выдачи:** если ни один абзац не прошёл минимальный порог совпадения значимых термов / близости, модель не вызывается (`aiStatus: 'weak_evidence'`); найденные слабые кандидаты возвращаются отдельно с пометкой «прямого ответа в каталоге не найдено, ближайшие места».
6. **Вызов модели (если `CONSULTANT_AI_ENABLED=true`):**
   - проверка семафора одновременных вызовов (`<= 3` in-flight) и атомарное резервирование слота в `usage_day` (`WHERE ai_calls < DAILY_AI_CALL_LIMIT`, стартовое значение `DAILY_AI_CALL_LIMIT=100`); если лимит исчерпан или семафор занят — возвращаются найденные абзацы без ответа ИИ (`budget_exceeded` / `busy`);
   - вызов `openai.responses.parse` (`maxRetries: 0`, таймаут `15 с`, `temperature: 0`) через `spoken-word.info/openai-proxy/v1`;
   - на вход подаются только отобранные абзацы в виде структурированных данных `{ id, author, documentType, documentTitle, creationDate, sitePublication, text, contextBefore, contextAfter, alsoIn }`;
   - схема ответа модели (Zod): `status: 'answered' | 'refused'`, `refusalReason` (при отказе), `blocks: Array<{ text: string, paragraphIds: string[] }>` (1..5 блоков). Цитаты и подписи авторов модель не дублирует.
7. **Жёсткая проверка ответа кодом:**
   - у каждого блока `paragraphIds.length >= 1`, и каждый `id` присутствует среди переданных в этом запросе кандидатов;
   - соблюдён потолок длины текста блока и всего ответа;
   - нет речи от первого лица Владыки вне кавычек (`/^Я,\s+[А-ЯЁ]/mu`, «Я ЕСМЬ ваш», «мои возлюбленные чела» и т. п.);
   - для каждого блока код сам собирает список авторов и типов документов из его `paragraphIds[]`, а для карточек подставляет дословный `paragraph.text` и ссылки `https://amasters.ru/pearls/{siteYear}/{slug}#d{d}-p{p}` из БД.
8. **Безопасная деградация:** при таймауте, ошибке прокси, невалидной схеме или провале проверок шага 7 пользователь всё равно получает HTTP `200` с найденными карточками абзацев и `aiStatus: 'error'` («ИИ-сводка временно недоступна, показаны найденные абзацы»).

### Фаза 2. Сервис `amasters-ai`: синхронизация и поиск абзацев без ИИ (4–5 дней)

В конце фазы уже работает полноценный справочник абзацев с точными ссылками, не расходующий бюджет OpenAI (`CONSULTANT_AI_ENABLED=false`).

1. Создать репозиторий `moscow/amasters-ai/`: Express 5 + React/Vite, строгий TypeScript, ESM, `lint`, `test` (`tsx --test`), `build`, `/api/health` с `SELECT 1` и таймаутом 3 с (`200 {"ok":true}` / `503 {"ok":false}`).
2. Подготовить инфраструктуру на Москве (`ssh sw` / `ssh app` по правилам `moscow/AGENTS.md`):
   - БД и роль `amasters_ai` (лимит соединений, `REVOKE ALL ON DATABASE amasters_ai FROM PUBLIC` сразу после `CREATE DATABASE`);
   - read-only роль `amasters_ai_reader` с `CONNECT` и `SELECT` на `"Pearl"`, `"PearlDocument"` в `pearls_migrator` (`PEARLS_DATABASE_URL` в `shared/.env`, в то время как `DATABASE_URL` указывает строго на `amasters_ai`);
   - DNS `ai.amasters.ru`, vhost `nginx` (`proxy_set_header X-Forwarded-For $remote_addr;`, `limit_req`, TLS через certbot), `ecosystem.config.cjs` с абсолютными путями Node `v24.22.1`.
3. Реализовать команду `npm run sync`:
   - чтение источника в `REPEATABLE READ READ ONLY` транзакции, валидация строк через Zod, отказ от перезаписи если `pearls < 250` или `documents < 300`;

   - запись в `amasters_ai` в одной транзакции.
4. Реализовать ступенчатый полнотекстовый поиск, режим `catalog_list`, словарь синонимов, склейку дублей с `alsoIn[]`, отбор до 3 абзацев с документа (всего до 8) и порог `weak_evidence`.
5. Собрать одностраничный интерфейс: поле вопроса, фильтры «Автор» и «Тип материала» (`GET /api/filters`), карточки источников по выпускам, раскрытие соседнего абзаца («Контекст») и дублей («Есть ещё в N выпусках»), ссылка «Читать в выпуске», дисклеймер о границах, `noindex` и `robots.txt`.
6. Реализовать `npm run check:links`: обход всех 252 выпусков через `http://127.0.0.1:3021/pearls/{siteYear}/{slug}` и сверка того, что для каждого абзаца из БД консультанта на HTML-странице есть `<p id="d{d}-p{p}">` с **тем же нормализованным текстом**.

### Фаза 3. Смысловой поиск в памяти процесса (2 дня, если нужно поднять полноту)

Выполняется, если в Фазе 2 перефразированные вопросы («тот же смысл другими словами») не дотянули до целевой полноты или решено сразу довести `recall@8` до `>= 0,85`.

1. Команда `npm run embed`: считает недостающие векторы (`text-embedding-3-small`, `dimensions: 512`) по `window_hash` для абзацев с `is_separator = FALSE`, пишет L2-нормированный `Float32Array` в `embedding.vector` (`BYTEA`). Идемпотентна, при обрыве продолжает с места остановки.
2. При старте сервера и по сигналу после `embed` векторы загружаются в один типизированный буфер `Float32Array` (~71 МБ в ОЗУ; `max_memory_restart: '512M'` в PM2). Если таблица `embedding` пуста или эмбеддинг вопроса не получен (прокси недоступен) — поиск прозрачно работает на одном полнотексте.
3. Гибридное ранжирование: слияние рангов полнотекста и косинусной близости через RRF с сохранением фильтров `authorSlug` / `documentType` и калибровкой порога `weak_evidence` по золотому набору.

**Критерий выхода Фазы 3:** на золотом наборе `recall@8 >= 0,85` на отвечаемых вопросах при сохранении `weak_evidence >= 0,90` на вопросах «вне корпуса»; время векторного прохода в процессе `< 25 мс`; при отключённом прокси поиск без ошибок откатывается на полнотекст; потребление RSS процесса под нагрузкой `< 300 МБ`.
