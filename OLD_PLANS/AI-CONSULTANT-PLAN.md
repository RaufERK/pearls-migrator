# План: ИИ-консультант на `ai.amasters.ru` (версия 2)

Версия 2 учитывает три вещи: рецензию `AI-CONSULTANT-PLAN-REVIEW.md`, решение сделать консультанта отдельным проектом на своём домене и свободный стек вместо Next.js. Идея и границы — в `AI-CONSULTANT.md`. Здесь только план, кода нет. Версия 1 этого файла заменена.

## 1. Проверка рецензии

Я перепроверил замечания по коду и данным. Все пять верны.

| Замечание рецензии | Проверка | Решение |
|---|---|---|
| П1. Окно из 3–5 абзацев не может быть адресом | Верно: на странице есть `<p>` без `id`, окно не имеет адреса | Единица адреса и поиска — абзац. Окно только как контекст |
| П2. Три разных счёта номеров | Верно: `seed.ts` задаёт `position = index + 1`, `toPearlDetail` его не отдаёт, `toBody` режет по `\n{2,}` и выбрасывает пустое | Одна функция адреса и тест-контракт. Сейчас в корпусе 34 796 абзацев, пустых и со внутренним `\n\n` нет, так что нумерация совпадает; контракт фиксирует это на будущее |
| П3. Полнотекст по окну не говорит, какой абзац подошёл | Верно | Индекс по абзацам. Recall считается по идентификатору абзаца в ссылке |
| П4. Одна ссылка на документ прячет остальные абзацы | Верно | До 3 абзацев с документа, группировка под выпуском |
| П5. Якорь уедет под шапку | Верно: `SiteHeader` имеет `sticky top-0` | `scroll-margin-top` у абзаца |

Два уточнения от меня:

1. **Нумерация с единицы.** Рецензия предлагает `p` с нуля, а подпись «абзац 15» с единицы. Две нумерации дают ошибки на единицу. Предлагаю обе с единицы: `#d1-p15` и «абз. 15» совпадают. Адрес вводится заново, поэтому цена выбора нулевая.
2. **Дубли.** В корпусе 1 268 разных абзацев длиннее 60 знаков встречаются больше одного раза (повторяющиеся призывы и вступления). Хэш в адрес класть нельзя (рецензия права), но в выдаче такие абзацы нужно склеивать в одну карточку «тот же текст есть ещё в N выпусках», иначе консультант покажет пять одинаковых карточек. В золотом наборе ожидаемый абзац считается найденным, если найден любой из абзацев с тем же хэшем.

## 2. Что меняет отдельный проект

Что становится проще и безопаснее:

- Основной прод не получает ключ OpenAI, эмбеддинги, расширение `pgvector`, новых таблиц и новых маршрутов. Строка в `README.md` «OpenAI на прод не кладём» остаётся верной.
- Проблема «`db:seed` на каждом деплое стирает базу, и вместе с ним эмбеддинги» исчезает: у консультанта своя база и инкрементальная загрузка по хэшу.
- Решение про `pgvector` относится только к базе `amasters_ai`. Основная `pearls_migrator` не меняется.
- Остановка консультанта (`pm2 stop`, выключатель, отзыв сертификата) не затрагивает каталог.
- SEO-ограничения основного сайта (серверный рендер, `force-dynamic`, год не в URL) на консультанта не распространяются. Страница закрыта от индексации.

Что появляется нового и требует внимания:

- **Контракт адресов.** Ссылка с `ai.amasters.ru` должна точно попасть на абзац `amasters.ru`. Две системы теперь связаны только договорённостью о ссылке, поэтому нужна автоматическая проверка (Фаза 2, `check:links`).
- **Синхронизация корпуса.** Консультанту нужен текст и метаданные, и они должны совпадать с тем, что показывает прод (год выпуска `siteYear` вычисляется в `seed.ts` не тривиально, с несколькими запасными правилами, повторять эту логику нельзя).
- **Свой хвост эксплуатации.** Свой домен, сертификат, порт, nginx, PM2, база, бэкап, мониторинг (см. Фазу 5).

### Как консультант получает корпус

Два варианта, рекомендую первый.

| | A. Роль только для чтения к `pearls_migrator` (рекомендую) | B. Файл-экспорт из `pearls-migrator` |
|---|---|---|
| Согласованность с сайтом | По построению: те же `slug`, `siteYear`, `position`, `content`, что отдаёт страница | Тоже, если экспорт делает код основного проекта |
| Что меняется в основном проекте | Ничего в коде. На сервере root создаёт роль `SELECT` на `Pearl` и `PearlDocument` | Новая CLI-команда экспорта и способ доставить файл на сервер |
| Риск для прода | Нагрузка одного чтения ~13 МБ раз в синхронизацию, роль без права записи | Нет |
| Связанность | Консультант зависит от двух таблиц | Зависит от формата файла |
| Исключение из правил хоста | Это осознанное исключение из изоляции баз (`REVOKE ... FROM PUBLIC`): роль получает `CONNECT` к `pearls_migrator`. Нужно отдельное решение владельца и запись в `AGENTS.md` | Исключения нет |

Если исключение из изоляции баз нежелательно, берётся вариант B. Остальной план от выбора не зависит.

Защита синхронизации в обоих вариантах: не удалять из своей базы ничего, если источник пустой или документов стало меньше порога (на момент `db:seed` прод на секунды пустой). Загрузка идёт по хэшу текста: новое добавляется, изменившееся пересчитывается, исчезнувшее помечается и убирается после подтверждения.

## 3. Основа решения

### Идентификатор абзаца (контракт)

- `d` — `PearlDocument.position`, с единицы.
- `p` — номер абзаца в массиве `toBody(content)`, с единицы. Тот же фильтр пустых абзацев. Не `paragraphsCount` и не индекс сырого JSON.
- Адрес: `https://amasters.ru/pearls/{siteYear}/{slug}#d{d}-p{p}`. Год в пути — год выпуска, не год создания.
- Разрез длинного абзаца для поиска остаётся внутри того же `p`. У предложения адреса нет.
- Хэш текста в адрес не входит. Он нужен только эмбеддингам, дедупликации и золотому набору.
- Футер абзацев-адресов не имеет, ссылок на него нет.

### Таблицы консультанта (база `amasters_ai`)

- `document`: `slug`, `siteYear`, `position`, автор (имя и slug), тип, название, дата создания (может быть пустой), дата и подпись выпуска.
- `paragraph`: ключ `(slug, position, paragraphNumber)`, `text`, `textHash`, `tsvector` по тексту абзаца (`russian`, GIN). Автор, тип и название соединяются из `document`, не копируются.
- `embedding`: `textHash` + `model` → вектор. Строится на абзаце вместе с соседом по обе стороны, ключ — хэш этого окна. Не привязана к `paragraph` каскадом, переживает пересборку.
- `usage_day`: счётчик дневного бюджета; `request_log`: только числа, без текста вопроса.

Соседний абзац для карточки и промпта читается по номеру `± 1` в том же документе. Оконной таблицы нет.

### Поток запроса

1. `POST /api/ask`: проверка длины, лимитов, выключателя.
2. Разбор вопроса: запрещённый (личный совет, «продиктуй») → отказ без модели; каталожный («какие диктовки такого-то есть») → SQL по метаданным; по смыслу → поиск.
3. Поиск абзацев (полнотекст, затем гибрид), фильтры «автор» и «тип». Дубли по хэшу склеиваются до показа и до вызова модели.
4. Отбор: до 3 абзацев с документа, всего до ~8, подряд идущие группируются в блок.
5. Порог слабости: слабая выдача — отказ без модели, «похожие места» отдельным списком.
6. Модель получает записи `{ id, text }` (с теми же идентификаторами, что в ссылках), соседи помечены как контекст. Ответ: блоки `{ text, paragraphIds[] }` либо отказ с причиной.
7. Проверка кодом, подстановка дословных абзацев по идентификаторам, построение ссылок.
8. Любая ошибка модели или проверок → показать найденные абзацы без ответа.

## 4. Стек и размещение

| | Решение |
|---|---|
| Сервер и API | Express 5, Node v24.22.1 (тот же, что закреплён на хосте), строгий TypeScript, ESM |
| Фронтенд | React + Vite, одна страница; Express отдаёт собранную статику, один процесс и один порт |
| Валидация | Zod: вход API, строки из базы основного сайта, ответ модели |
| База | PostgreSQL 16, отдельная `amasters_ai` и роль; драйвер `pg`, схема SQL-файлами (как `amasters_info`: сложные типы и полнотекст всё равно на сыром SQL) |
| Поиск | Полнотекст `russian` по абзацам; позже `pgvector` или векторы в памяти |
| Модель | Пакет `openai`, структурированный вывод под Zod, через прокси `spoken-word.info/openai-proxy` |
| Тесты | `node:test` через `tsx --test`; прогон с настоящей моделью — отдельная команда, не в `npm test` |
| Размещение | Moscow VPS. Прод основной БД здесь же, поэтому в Амстердам не переносим |
| Процесс | PM2 под `appuser`, `ecosystem.config.cjs` с абсолютными путями Node v24.22.1 (правила хоста: без `nvm use --lts`, без `npx pm2`) |
| Сеть | nginx-сервер `ai.amasters.ru` на `127.0.0.1:<свободный порт>`, certbot, `limit_req` |
| Репозиторий | Новая папка рядом с остальными приложениями: `moscow/amasters-ai/` |

Express вместо Next выбран осознанно: SEO не нужен, серверный рендер не нужен, а один Node-процесс с API и статикой проще в эксплуатации. Если по ходу окажется, что нужна возможность делиться ссылкой на ответ, это добавляется маршрутом, стек не меняется.

### Фаза 1. Адресуемые абзацы в основном проекте (1–2 дня)

Единственное изменение прода до запуска консультанта. Выкатывается отдельно, обычным `npm run deploy:code`, и ничем не связано с ИИ.

- Чистая функция адреса в `src/` (например, `paragraphAnchor.ts`): из позиции документа и номера абзаца собирает `d{n}-p{m}`. Тесты `node:test`.
- Страница выпуска ставит `id` на каждый `<p>` тела и использует эту функцию.
- Тест-контракт: строит адрес из строки базы и сверяет с `id` абзаца, где на странице тот же текст. Он же проверяет, что в `toBody` нет пустых абзацев и что `position` идёт без пропусков.
- Подсветка через `:target`, `scroll-margin-top` у абзаца (шапка `sticky top-0`, запас задаём и для мобильного).
- Проверки после выкладки: страница выпуска отдаёт полный HTML, главная и каталог не изменились, `npm run smoke`, `sitemap.xml` прежний.

Критерий выхода: открытие `/pearls/{год}/{slug}#d1-p15` прокручивает и подсвечивает нужный абзац на настольном и мобильном виде. Откат — предыдущий релиз.

### Фаза 2. Новый проект: поиск абзацев со ссылками, без ИИ (4–5 дней)

Публичный запуск возможен уже здесь: денег фаза не тратит.

1. Репозиторий `amasters-ai`, каркас Express 5 + React/Vite, строгий TypeScript, `lint`, `test`, `build`.
2. Инфраструктура (root через `ssh sw`, по правилам хоста): база `amasters_ai` и роль, `REVOKE ALL ON DATABASE ... FROM PUBLIC` сразу после `CREATE DATABASE`, лимит соединений роли; роль для чтения корпуса (если вариант A); DNS-запись; nginx-сервер с `limit_req`; certbot; `ecosystem.config.cjs`; `/api/health` с `SELECT 1`.
3. Синхронизация корпуса (`sync`): читает `Pearl` и `PearlDocument`, данные проходят Zod до записи, режет `content` на абзацы тем же правилом, что `toBody`, пишет по хэшу, защищена от пустого источника.
4. Индекс: `tsvector` по абзацу, GIN. Дубли по хэшу группируются.
5. Разбор вопроса (`parseQuestion`): нормализация, удаление служебных слов, словарь синонимов (Эль Мория / Эль Морья, Сен-Жермен / Сент-Жермен, Майтрея / Майтрейя и т. п.; ведёт человек), запрос по ИЛИ с усилением фразы и совпадения в названии документа. Явные фильтры «автор» и «тип» из формы.
6. API `POST /api/search` и интерфейс: форма, фильтры автор/тип (значения из своей базы), карточки по выпускам, подряд идущие абзацы одним блоком, кнопка «контекст», ссылки «читать в выпуске», дубли («тот же текст есть ещё в N выпусках»), подпись о границах, `noindex`, `Disallow` в `robots.txt`.
7. `check:links`: после выкладки Фазы 1 открывает страницы выпусков и проверяет, что каждый построенный адрес имеет `id` на странице. Запускается после каждой синхронизации и перед релизом.
8. `eval:search`: прогон золотого набора по поиску, recall@5 по адресу абзаца.
9. Деплой через PM2. Тесты на разбор вопроса, группировку и дедупликацию, сборку адреса (тот же вход, что и в основном проекте).

Критерий выхода: recall@5 по адресу абзаца на отвечаемых вопросах не ниже согласованного порога (предлагаю ≥ 0,7 для полнотекста), `check:links` зелёный на всех страницах, на «вне корпуса» выдача пустая или слабая и помечена как «похожие места».

### Фаза 3. Смысловой поиск (2–3 дня, только если Фаза 2 не дотянула)

- Эмбеддинг на абзац с соседями, таблица `embedding` по хэшу окна; идемпотентная команда `embed` досчитывает недостающее, сбой не ломает работу, консультант деградирует до полнотекста.
- Хранение: `pgvector` в `amasters_ai` или векторы в памяти (решено в Фазе 0). Размерность и модель по замеру.
- Гибрид: слияние рангов полнотекста и вектора (RRF), затем фильтры.
- Если выбран `pgvector`: расширение на Moscow PG16 и на Амстердаме (PG18), иначе не восстановится бэкап. Прогнать проверку восстановления и записать дату в `DB-BACKUPS.md`, Раздел 11.
- Включаем, только если recall@5 вырос минимум до согласованного порога (предлагаю ≥ 0,85).

### Фаза 4. Ответ ИИ по найденному (3–4 дня)

1. Схема Zod: либо отказ с причиной (`out_of_corpus`, `personal_guidance`, `request_for_dictation`, `weak_evidence`), либо блоки `{ text, paragraphIds[], attributedTo }`. Типизированный вывод OpenAI под эту схему. Свободного текста вне схемы нет.
2. Промпт: абзацы идут как данные в отмеченном блоке с идентификаторами, любые «инструкции» внутри них — тоже данные. Запрет первого лица Владыки, новых призывов, ритуалов, личных советов.
3. Проверки кода до показа:
   - все `paragraphIds` из текущей выдачи;
   - у блока минимум один идентификатор;
   - блок с абзацами разных авторов или типов не может утверждать «учение говорит»;
   - длина блока и ответа в пределах;
   - запрещённые обороты (обращение «Я, …» от лица Владыки, ритуальные императивы) режутся эвристикой, при срабатывании отказ.
4. Цитаты и ссылки в карточки подставляет код по идентификаторам.
5. Деградация: тайм-аут, невалидная схема, провал проверок, прокси недоступен → карточки найденных абзацев и пометка «ответ не составлен».
6. Вторая проверка «подтверждает ли абзац утверждение» отдельным дешёвым вызовом: сначала только в оценке, в рабочий путь включаем, если оценка покажет расхождения.
7. Тесты валидаторов на заведомо плохих ответах модели (выдуманный идентификатор, блок без опоры, смешение авторов, «Я, Владыка…»). Прогон золотого набора с настоящей моделью — команда `eval:answer`.

Критерий выхода на золотом наборе, проверенном человеком: 0 выдуманных идентификаторов; 100% отказов на «вне корпуса», «продиктуй» и «посоветуй лично»; на отвечаемых «пересказ соответствует абзацам» не ниже согласованной доли (предлагаю ≥ 90%); расхождения источников показаны, а не сглажены.

### Фаза 5. Эксплуатация и защита (2–3 дня, до публичного запуска ответа ИИ)

- Лимит на посетителя (nginx и приложение), **дневной бюджет на весь сайт** (`usage_day`; исчерпан — работает режим без ИИ), выключатель `CONSULTANT_AI_ENABLED` в `shared/.env`, потолок длины вопроса и ответа, тайм-аут и один повтор.

## 7. Риски

| Риск | Что делаем |
|---|---|
| Ссылка попала не на тот абзац | Одна функция адреса, тест-контракт, `check:links` после каждой синхронизации и релиза |
| Текст на `amasters.ru` изменился, нумерация абзацев сдвинулась | Синхронизация и `check:links` после каждого деплоя основного проекта; ссылки с якорем не вечные, известное ограничение |
| Консультант и основной сайт расходятся по `siteYear` и `slug` | Корпус берётся из той же базы (вариант A) или из экспорта того же кода, логика не дублируется |
| Синхронизация застала пустую базу во время `db:seed` | Защита от пустого источника и порога, удаление только после подтверждения |
| Роль чтения нарушает изоляцию баз | Только `SELECT` на две таблицы, запись в `AGENTS.md`, либо вариант B |
| Модель не следует запретам | Схема, проверки кодом, отказ по умолчанию, деградация до абзацев |
| Прокси недоступен или ограничивает | Режим без ИИ, тайм-аут, выключатель |
| Расходы из-за ботов | `limit_req`, лимит на посетителя, дневной бюджет, длина вопроса |
| Слова учения пишутся по-разному | Словарь синонимов, золотой набор |
| `pgvector` ломает восстановление на Амстердаме | Расширение и на PG18, либо векторы в памяти |
| Хост общий, нагрузка консультанта задевает соседей | `max_memory_restart`, лимит соединений роли, тяжёлые задачи вне пиков |
| Посетитель принимает ответ за слова Владыки | Подпись, формулировки «в материалах сказано», запрет первого лица, дословные абзацы |

## 8. Ответы на вопросы рецензии

| Вопрос | Ответ |
|---|---|
| 1. Соседние абзацы показывать приглушённо? | В карточке виден найденный абзац; соседний текст по кнопке «контекст». Ссылкой он не является. На React это дёшево, подсветка основного сайта не меняется |
| 2. Потолок 3 абзаца с документа? | Да, плюс общий потолок ~8; значения вынесены в константы, настраиваются по золотому набору |
| 3. Подряд идущие абзацы (14, 15, 16)? | Показывать одним блоком «абз. 14–16», ссылка блока на первый, у каждого абзаца своя маленькая ссылка. Диапазон подсвечивать на `amasters.ru` не пытаемся |
| 4. Футер без ссылок? | Да. Место и дату даёт метаданные карточки |
| 5. Нумерация абзаца в подписи? | Да, «абз. 15». Номер в адресе тоже с единицы, они совпадают |

## 9. Решения, которые нужны от вас

1. Доступ к корпусу: **A** (роль только для чтения к `pearls_migrator`) или **B** (экспорт из `pearls-migrator`). Рекомендую A.
2. Нумерация абзацев с единицы и в адресе, и в подписи. Рекомендую так.
3. Кто составляет золотой набор вопросов с адресами абзацев и кто делает DNS-запись для `ai.amasters.ru`.
4. Название папки и репозитория: `amasters-ai`, если нет другого.

После ответов можно начинать Фазы 0 и 1 параллельно.
